## 一、目标、架构与工作流

> 更新：2026-10-08。产品定位为 WhoAmI OS；本地最小版已具备代码实现。四层架构和执行契约仍是设计基线，访谈细节继续验证。

### 1. 目标

**产品从第一版起就是 WhoAmI OS。第一版交付本地最小版，`who-am-i` Skill 是其中一个交互入口。** 核心价值是让不同 AI 在有限、相关且可追溯的上下文中理解一个人。`who-am-i` 将个人模型能力带入一个 AI 宿主；OS 负责统一的人物模型、记忆治理与工作流，为其他任务提供个人上下文，最终决策仍由用户作出。它通过逐层访谈形成基础个人模型，之后根据用户确认的新信息持续更新，使 AI 能理解一个人的背景、目标、偏好、现实约束、内在张力和变化方向，并说明每项判断的来源与适用时间。

第一版的设计顺序是：**确定认识维度 → 设计由浅入深的提问 → 形成基础了解 → 经用户确认写入 → 在后续使用中复查与更新**。不能为了填满所有栏目而猜测用户，用户可以跳过或暂停任何问题。

### 1.1 从第一天分层

| 层 | 职责与边界 | V1 落地 |
| --- | --- | --- |
| Core | 定义 Person Model、schema、证据、时间、敏感信息与更新规则；不绑定某个模型或平台 | 通用规范及模板；沿用下文八个认识维度 |
| Memory | 保存用户的人物记录、证据、历史和派生摘要；数据归用户掌控 | 独立目录中的 Markdown/YAML；本地读写模块统一访问，Git 可选 |
| Skills | 按 Core 规则操作 Memory，完成 Initialize / Recall / Update | 一个 `who-am-i` Skill 内的三个工作流；调用本地读写模块 |
| Adapters | 将同一模型和工作流接入 AI 宿主、MCP/API 等；不得绕开记忆治理 | V1 实现一个本地宿主接入并定义加载约定；后续扩展多端 |

从产品能力看，OS 自第一版起同时包含 **Identity（人物模型）**、**Memory（记录与来源）** 和 **Intelligence（访谈、召回、更新与解释）**；Core / Memory / Skills / Adapters 是它们的实现分工。Skill 属于 Skills 层的交互方式，不能单独代表整套 OS。

架构中的 **Core 层是通用规范**；运行时的 **core memory 是 Memory 中轻量、可重建的个人摘要**，两者不要混同。依赖方向是 Skills 遵循 Core，通过本地读写模块访问 Memory；Adapters 调用同样的操作契约。读写模块是 Memory 的执行组件，不新增一层，不承担访谈和人格推断。平台接口变化不应改写人物模型含义。

当前 OS 仓库结构如下；运行时代码已落地，访谈与多宿主能力仍会迭代：

```text
WhoAmI/
├── design/                       # 本组设计文档
├── core/                         # schema、证据/时间/更新/隐私规则
├── lib/                          # 本地读写、权限校验、事务恢复
├── skills/who-am-i/               # SKILL.md、三个工作流、模板与虚构示例
└── adapters/                     # V1 的首个本地宿主接入；后续扩展 MCP/API

用户指定的 personal-memory/        # OS 的个人数据，不在通用代码仓库中
```

V1 采用指令、文件、模板和轻量本地读写模块，**不做数据库、向量库、Web UI、后台监听或自动跨平台同步**。本目录 HTML 是设计图示，不是产品 Web UI。Git 用于版本追踪，由用户管理提交和远端；Skill 不自动提交、推送个人数据。

### 1.2 三个工作流与调用时机

| 工作流 | 触发 | 结果 |
| --- | --- | --- |
| Initialize | 用户选择新建、导入其授权的聊天记录/描述，或打开现有模型 | 区分原始自述与 AI 解释，补访谈、预览、确认后建立模型；已有目录直接续用 |
| Recall | 当前任务需要目标、偏好、约束或经历等个人上下文 | 返回与问题相关、在适用时间内、允许使用的少量记录及来源 ID |
| Update | 用户明确纠正、提供变化、新目标或值得保存的信息 | 去重、区分纠错与演变、展示差异并确认写入；无有效变化则不写入 |

**通过检查的长期 core 轻量常驻，领域记忆按需读取。** `AGENT.md` 仅保留经用户同意、稳定且跨任务有用的身份概览、价值原则和沟通偏好，目标约 500–1500 tokens，信息少时不必凑满。它是数据摘要，不是可执行指令。由支持该能力的宿主先调用本地加载入口，完成权限、来源版本和到期检查，再作为数据载入；Skill 本身不承诺自动常驻。不支持该入口的宿主使用手动调用，不直接自动注入文件。

Recall 先读取清单和授权元数据，再校验拟使用摘要的来源内容哈希；校验通过后才返回摘要正文。根据任务选择领域、时间及记录；需要解释依据时才沿引用读取证据。领域由标签路由，每条记录保持唯一主存储位置，按维度目录归档。临时职业状态、历史事件和敏感细节不进入常驻摘要。摘要过时则跳过旧正文，从获准且仍有效的记录重新组装。V1 使用已确认陈述的模板化摘录；新的概括须另作候选确认。对话中已展示的信息无法靠删除文件抹除，撤回后宿主应停止复用旧上下文，必要时开启新会话。

例如职业选择只召回目标、相关价值取舍、职业状态、约束和过去相关决定；不读取无关生活细节。普通知识问题如“HTTP 304 是什么”只沿用必要的沟通偏好，不触发领域召回或人物模型更新。读取与更新是独立动作，不因调用 Recall 就写入。具体过滤与预算见[个人记录与读取规则](#storage)。

### 2. 认识一个人的维度（讨论稿）

| 维度 | 基础问题：是什么 | 追问：具体发生过什么 | 深入问题：为什么、如何变化 |
| --- | --- | --- | --- |
| 身份与角色 | 你现在怎样介绍自己？承担哪些主要角色？ | 哪些角色占据你最多时间？ | 过去几年，你对自己的定位发生过什么变化？ |
| 关键经历 | 哪些经历对你影响最大？ | 当时发生了什么，你作了什么选择？ | 它怎样改变了你之后的想法或行为？ |
| 价值取舍 | 哪些事情对你很重要？ | 最近一次在两件重要事情之间选择时，你怎么选？ | 什么条件会改变你的取舍？ |
| 目标与方向 | 你现在最想推进什么？ | 为什么是这个目标，怎样判断有进展？ | 它与长期方向一致吗？近期方向有变化吗？ |
| 偏好与协作 | 你喜欢怎样的沟通和协作方式？ | 什么样的回答或合作真正帮到过你？ | 不同任务下，你对速度、细节和主动性的要求会变吗？ |
| 决策方式 | 做重要决定时，你通常先看什么？ | 能用近期一次选择说明吗？ | 什么证据会改变你的观点？你如何看待可逆性和最坏结果？ |
| 行为模式 | 哪些事情你容易投入或拖延？ | 最近一次是什么情况？此前有类似例子吗？ | 通常什么条件会触发？有哪些例外？ |
| 关系与约束 | 哪些人或现实条件会影响你的选择？ | 它们具体影响过什么决定？ | 哪些是暂时约束，哪些是长期责任？ |

这八项是**提问的入口**，不是要求每人都填满的固定问卷。「当前状态」记录某个维度在此时的情况；「内在张力」关联两个同时存在的诉求；「变化方向」比较前后记录。后三者属于跨维度的综合结果，需要时间和证据支持，不应在初见时强行给出结论。

#### 访谈节奏

每轮提出一到两个有关联的问题。先取得基础概览，再根据用户认为重要的领域追问具体事件、选择依据和变化。优先使用开放问题；对模糊答案追问例子，对用户不愿谈的领域直接跳过。允许暂停和续聊。

快速模式覆盖关键维度的基础问题，并对一两个最重要的维度追问，形成可供新 AI 使用的基础了解。深入模式沿相同维度继续探讨经历、价值排序、决策方式、行为条件和变化。两种模式的区别是深度与覆盖范围，使用同一模型。

基础了解的完成标准：能够用用户认可的表述说明其当前角色、近期目标、主要约束、协作偏好，以及至少一项对选择有影响的经历或价值取舍；未了解的方面清楚标注为未知。完成不以提问数量或维度覆盖率衡量。

### 3. 首次使用与现有记录

「本机第一次调用 Skill」不等于「没有个人模型」。当尚未确定记忆目录时，提供**新建个人模型**和**打开现有记录**两个入口。个人数据目录由用户指定，与通用 OS 仓库分开。迁移电脑后，用户可重新选择带来的记录目录。

读取选定目录后，再判断状态：

| 状态 | 行为 |
| --- | --- |
| 没有可用模型或模型为空 | 进入快速或深入访谈。 |
| 清单、维度文件与时间线中存在有效记录 | 读取已有内容，展示简要概览与待复查项，再继续访谈、查询或更新。 |
| 文件缺失、损坏、格式版本不兼容，或只有摘要 | 停止写入，说明问题，提供恢复或迁移预览；不创建空文件覆盖现有资料。 |

本机可记住上次使用的目录作为便利入口。结构化记录是模型状态的依据；`AGENT.md` 是从记录得到的可读摘要。

### 4. 回答如何成为记忆

每条候选内容同时标明**内容维度**和**判断性质**：

| 性质 | 含义 |
| --- | --- |
| `fact` | 有明确来源的具体信息；注明是用户自述还是其他资料。 |
| `state` | 当前处境、感受、意向或临时约束，带时间语境。 |
| `interpretation` | AI 基于资料提出的解释，说明依据与不确定性，单独请用户确认。 |
| `pattern` | 多个独立事件支持的反复倾向，说明适用情境和例外。 |

记录至少包含：稳定 ID、性质、维度、简短陈述、适用情境、证据来源或必要摘录、记录时间、已知的有效时间、复查时间、状态与关联记录。无法确定的时间留空，不补猜。用户确认一项陈述，表示同意保存这一表述；解释仍然是解释，不能因确认而自动变成事实。

写入前展示新增、修改、失效、删除的具体内容和原因，允许用户确认全部、确认部分、编辑后确认或拒绝。只写入确认的部分；经过实质修改的内容重新展示。未确认候选只存在于当前会话，不能在新会话中假装已保存。

一次情绪或想法不升级为稳定人格或行为模式。同一事件的多次转述不构成多个独立证据。第一版只有在至少三个独立事件、跨两个日期时才提出模式候选，之后仍需用户确认。用户明确陈述的价值观可以保存为自述；AI 从行为推断出的排序保留为解释。

同一信息再次出现时在确认后补充证据；用户指出记录错误时更正旧记录及其派生结论；情况发生变化时保留旧记录的历史有效期并建立后续记录。冲突先核对时间和情境，无法解释时标为待澄清。到达复查时间表示需要询问，不能直接断言旧状态已经结束。忘记指定信息时清理当前记录、保存的摘录及派生摘要，并说明 Git 历史是否仍包含该信息。

### 5. 第一版文件结构与使用

通用 OS 仓库计划包含 schema 和更新规则、本地读写模块、首个宿主接入、`who-am-i` Skill、模板及虚构示例。当前推荐的个人目录包含 `manifest.yaml`、按维度组织且每条记录独立文件的 `model/`、按记录年份组织且每条事件独立文件的 `timeline/` 和派生摘要 `AGENT.md`。时间线保存事件及证据，模型记录保存判断并通过 ID 引用事件；每份内容只有一个维护位置。摘要需标注生成时间和相关记录 ID，冲突时依据模型与事件记录重建。该结构保留现有分维度与时间线设计，作为 V1 基线；新增证据等级、领域标签和敏感控制，详见存储稿。

字段含义、写入确认、按任务读取、迁移与异常处理见[个人记录与读取规则](#storage)。

Git 用于用户自行追踪版本。第一版采用指令、模板和本地读写模块，不实现数据库、Web UI 或后台监听。Skill 不自动提交或推送个人数据。查询或协作时按当前任务选取相关记录；旧摘要和 AI 的既有回答不得循环成为新证据。

### 6. 三个成功测试（本地最小版退出条件）

以下测试均用虚构资料执行，记录输入、实际读取的文件/记录 ID、变更预览、保存结果和回答，逐项判定。这里定义验收方法，不代表已执行通过。

| 测试 | 输入与步骤 | 通过标准 |
| --- | --- | --- |
| 冷启动理解 | 提供一段有来源的访谈，含角色、目标、约束、偏好及一项价值取舍；用户跳过一个问题。确认后在无原聊天的新会话加载 core，并按任务召回 | 新 AI 准确说明五类已知信息、明确未知；每条陈述可追溯；没有虚构人格；迁移原目录可继续，无需重复整轮访谈 |
| 记忆更新 | 先保存“考虑换工作”，同一事件重复表达；后来“决定先留下”，再纠正一条误读；仅确认部分变更，并模拟一个到期复查项 | 重复不增独立证据数；变化保留旧状态和前后关联；纠错撤回误读并复查派生解释；仅保存确认项；到期只提示复查；摘要与引用一致 |
| 个性化决策 | 给出两个职业选项及已确认的目标、约束、价值取舍；加入无关领域记录、过时状态及禁止召回的敏感信息。对比无记忆、仅沟通偏好与完整 Recall 三组回答，再改变一项已确认约束重跑 | 建议至少明确关联两条相关记录，解释选项与约束的取舍；新约束改变建议或清楚解释为何不变；缺信息时询问而不编造；不读取禁止召回/无关内容，不把解释或过时状态当事实；最终选择权在用户 |

三项都通过，并满足下列回归场景和 [验收清单](#acceptance)，才扩展到多端版；不能仅以“记住了更多信息”或回答更长作为成功。

#### 保留的回归场景

1. 新用户可选择快速或深入访谈，跳过部分话题后仍能得到有用的基础概览。
2. 迁移电脑的用户打开原有目录后，直接看到现有模型并继续使用。
3. “最近想离职”只形成有时间语境的状态候选。
4. AI 提出价值取舍或内在张力时，展示依据和不确定性，并单独确认。
5. 用户只确认部分预览时，只有相应记录写入。
6. 更正与变化被分别处理；依赖旧信息的解释和摘要随之复查。
7. 重复转述同一事件不会增加模式证据数量。
8. 状态过了复查时间后提示询问，不推断相反结论。
9. 文件损坏或版本不兼容时不覆盖原记录。
10. 忘记操作清理当前可控文件，并说明 Git 历史的实际状态。

### 7. 路线图：WhoAmI OS 从本地到多端

| 阶段 | 交付与重点 | 进入下一阶段的依据 |
| --- | --- | --- |
| Phase 1 · WhoAmI OS 本地最小版 | 实现人物模型规则、本地记忆与读写模块、Initialize/Recall/Update、一个本地宿主接入；以 `who-am-i` Skill 作为首个交互入口 | 能从新会话读到获准上下文并完成确认式更新；三个成功测试、可靠性回归和用户帮助效果通过 |
| Phase 2 · WhoAmI OS 多端版 | 在复用 schema 的基础上建立记忆服务；按授权提取候选、检索、去重与时间复查，扩展 MCP/API 接入和用户授权的同步 | 不同客户端的召回一致、更新可审计，冲突及删除传播可验证；自动提取不等于自动批准写入 |
| Phase 3 · WhoAmI OS 跨领域版 | 在已运行的 Identity、Memory、Intelligence 能力上扩展跨领域理解、变化追踪与个人决策协作，由统一权限支撑多 Agent 使用 | 持续评估个性化帮助、可迁移性和用户控制；按真实需求扩展服务与交互形态 |

后续多端版可探索 `getProfile`、`recall`、`remember`、`getTimeline`、`getCurrentState` 接口，但签名与协议尚未承诺。数据库、索引或 Web UI 是否引入由后续规模与使用需求决定，不作为本地最小版依赖。迁移必须保留 ID、来源、时间语义和撤回/敏感设置。

### 8. V1 执行边界（本次补齐）

AI 负责理解与提出候选；本地模块负责能确定检查的操作。本地模块已实现部分确定性检查；不能把设计中的全部保证当成已通过验收。

| 责任 | AI / Skill | 本地模块 / 宿主 |
| --- | --- | --- |
| 理解 | 访谈、判断相关性、区分纠错与变化、解释取舍 | 校验字段、ID、引用和允许的状态变更 |
| 读取 | 提出领域、时间与所需记录，接收有限上下文 | 检查权限与发送目标，按记录读取，执行预算 |
| 保存 | 展示具体差异，收集全部或部分确认 | 将确认绑定到变更摘要和基础版本；成组提交、冲突拒绝、失败恢复 |
| 更新 | 提议新的判断，不自动批准自身推断 | 追踪事件 → 判断 → 解释 → 摘要；传播失效和权限限制 |
| 常驻 | 仅使用获准且验证通过的个人数据 | 先验证再返回摘要，失效时跳过或重建 |

最小操作契约为 `open`、`recall`、`prepare`、`apply`、`recover`；这是本地组件边界，不承诺网络 API。确认绑定 `model_id + base_revision + patch_hash + selected_change_ids`，变化后重新预览。普通查询不得顺便修改人物记录。

用户可以直接编辑文件；之后须通过导入检查重新接纳这些变更。不能把文件上的 `confirmed_at` 当成绕过权限的凭证。V1 的权限保证适用于遵循本地模块的宿主；它不阻止拥有目录访问权的其他程序直接打开文件。

先用“工作、目标与协作”完成 OS 的端到端试验；其他维度仍可由用户主动扩展，不要求填满。实现顺序：字段与授权契约 → 本地读写及恢复 → 三个工作流与 Skill 入口 → 首个宿主接入与加载 → 可靠性与帮助效果验收。详见 [个人记录与读取规则](#storage)、[执行与恢复契约](#runtime)与[验收清单](#acceptance)。

### 9. 待验证的产品细节

- 八个认识维度是否符合你期望的“了解一个人”；是否需要调整合并或顺序。
- 先以工作、目标与协作为主的试验是否足够有用；根据反馈调整扩展到其他领域的节奏。
- 基础了解完成标准是否足以让新的 AI 提供明显更贴合用户的帮助。

## 二、个人记录与读取规则

> 更新：2026-10-08。设计修订 2：保留维度、时间线、摘要三类职责；每条记录独立文件，补齐授权契约、依赖传播、读取预算与执行边界。本文对应 Memory 层，Core 定义规则，Skills 编排工作流，本地模块执行读写约束；Skill 入口已落地。

### 为什么调整

单文件便于最早验证格式，但长期查看目标、价值观、经历及其变化时，需要在同一文件里筛选大量记录。推荐从第一版就按认识维度组织，时间线承载实际发生的事件和可核查的表达，模型记录承载对用户的理解。两类内容通过 ID 关联，避免同一份证据在各文件中重复维护。

| 方案 | 适用情况 | 主要代价 |
| --- | --- | --- |
| 全部放入一个 YAML | 极少量资料的快速试验 | 人工阅读与按主题维护逐渐困难 |
| 只有分主题的 Markdown | 方便阅读当前画像 | 来源、前后变化和跨主题引用容易丢失 |
| 分维度模型 + 时间线 + 摘要（推荐） | 持续访谈、长期更新和迁移 | 需要维护 ID 引用及多文件一致性 |

### 个人目录

真实资料保存在用户指定的独立目录；通用 OS 仓库只放规则、代码、模板和虚构示例。以下是可形成的目录，不要求首次创建全部空文件。

```text
personal-memory/
├── manifest.yaml                 # schema/model/revision、记录路径、标签、策略、哈希、依赖元数据
├── policy.yaml                   # 用途/任务/目标/期限的授权记录，不以文件自证真实确认
├── AGENT.md                      # 获准稳定陈述的模板化派生摘要
├── model/                        # 维度是组织方式，每条记录只存一份
│   ├── identity/rec-….yaml
│   ├── experiences/rec-….yaml
│   ├── values/rec-….yaml
│   ├── goals/rec-goals-001.yaml
│   ├── preferences/rec-….yaml
│   ├── decisions/rec-….yaml
│   ├── patterns/rec-….yaml
│   ├── relationships/rec-….yaml
│   └── synthesis/rec-….yaml
├── timeline/2026/evt-20260930-001.yaml  # 按记录年份组织，一条事件一文件
└── .transactions/                # 仅确认后的短期事务与恢复材料，排除 Git
```

文件按第一次有确认内容时创建；每个文件只含一条记录或事件。个人目录与通用 OS 仓库分开迁移；清单中的路径全部相对个人目录，避免换电脑后路径失效。

### 三类内容各有职责

#### 时间线：发生过什么、用户表达过什么

`timeline/` 保存事件 ID、事件内容、发生时间、记录时间和必要来源摘录。例如一次职业选择、一段重要经历，以及用户在某日表达的意向。原始对话默认不全文归档；只保存足以核查的摘录与可用定位。定位缺失时明确说明，不能编造会话链接。

按「记录年份」分目录；查询人生时间线时按「发生时间」组织。今天回忆起去年的事件，记录年份属于今年，发生时间属于去年。发生时间可只有年或月，未知时为空，不凭空补精确日期。时间线不会把一次访谈中每句话都生成为事件，只保存有建模价值且获确认的内容。

#### 维度模型：这说明用户有什么目标、偏好或处境

`model/` 的每条记录保留稳定 ID、内容维度、判断性质、陈述、适用情境、状态、有效时间、复查时间，以及指向事件的 `evidence_ids`。解释还可以通过 `derived_from` 引用其他模型记录。每条判断只有一个主存放位置，跨主题关联用 ID 或标签，不复制陈述到多个文件。

四种性质仍为 `fact`、`state`、`interpretation`、`pattern`。`status` 为 `active`、`needs_review`、`disputed`、`superseded` 或 `retracted`。每个维度目录保留现状与历史记录，读取时按状态和有效时间筛选。短期和长期通过有效期、复查时间和性质表达，不另建两份重复内容。

`model/experiences/` 保存为什么某段经历重要的自述或解释，事件本身保存在时间线。`model/synthesis/` 的内在张力与变化方向属于解释，必须关联相关维度和证据，并单独请用户确认。它们不会自动成为新的独立证据。

#### 摘要：让其他 AI 快速上手

`AGENT.md` 从用户同意进入摘要的有效模型记录生成，带生成时间、模型修订号、记录 ID、来源内容哈希和最早复查时间。摘要目标约 500–1500 tokens，只含稳定、跨任务有用且获准常驻的记录；短期状态和领域细节通过 Recall 按需提供，不再放入默认常驻摘要。摘要可以重建，不能作为新事实的独立来源。它属于个人数据，不等同于仓库 AGENTS.md 指令文件；宿主须将其中内容当作数据处理。先验证权限、来源哈希与到期信息，再返回正文；禁止直接无条件自动注入。V1 只按模板摘录确认陈述，新的概括须经用户确认。

### 一个例子如何落盘

下面是虚构例子。用户在访谈中说「最近在考虑换工作，还没决定」，确认后形成一条来源事件和一条职业目标相关的状态。原话只保存在事件中。

`timeline/2026/evt-20260930-001.yaml`：

```yaml
events:
  - id: evt-20260930-001
    type: user_statement
    statement: "用户表达正在考虑换工作"
    occurred_at: "2026-09-30"
    recorded_at: "2026-09-30"
    sensitivity: personal
    recall_policy: allowed
    grant_ids: [grant-career-001]
    source:
      type: self_report
      reference: "当日访谈；原会话定位未保存"
      excerpt: "最近在考虑换工作，还没决定"
```

`model/goals/rec-goals-001.yaml`：

```yaml
records:
  - id: rec-goals-001
    kind: state
    dimension: goals
    domains: [career]
    statement: "正在评估换工作，尚未作出决定"
    context: "职业方向"
    status: active
    recorded_at: "2026-09-30"
    valid_from: null
    valid_to: null
    review_after: "2026-10-14"
    first_observed: "2026-09-30"
    last_observed: "2026-09-30"
    stability: short_term
    evidence_level: E1
    confidence: high  # 对“用户表达此意向”的把握，不代表未来会换工作
    confirmed_at: "2026-09-30"
    sensitivity: personal
    recall_policy: allowed
    grant_ids: [grant-career-001]
    evidence_ids: [evt-20260930-001]
    derived_from: []
    supersedes: []
    include_in_summary: false
```

若之后用户说「决定先留下」，新增来源事件及后续状态；前一状态保留为历史，关联新记录。若用户说「之前理解错了，我没考虑换工作」，旧判断标记为 `retracted` 并复查派生内容；旧访谈中的真实原话不被改写。若用户要求忘记这件事，预览并删除涉及的记录、摘录及派生内容，同时指出 Git 历史是否仍保留副本。

### 证据与时间字段规则

判断性质 `kind` 与证据等级是两个轴；证据强不自动把 `interpretation` 升为 `fact`。

| 证据等级 | 含义 | 使用约束 |
| --- | --- | --- |
| E0 · 推断 | AI 从已有记录推导，或来源尚无法核查 | 保留解释与依赖 ID；不得作为确定事实或独立证据 |
| E1 · 直接来源 | 一次明确自述，或一份用户授权的可定位资料 | 标注 self_report / document 等来源类型；证明该表达或材料存在，不表示所有内容已客观证实 |
| E2 · 独立重复支持 | 多个独立事件在不同时间支持同一倾向 | 模式候选至少三个独立事件、跨两个日期，记录情境与反例；仍需用户确认 |

`confidence` 使用 low / medium / high，表示对陈述在限定情境中的把握，不是统计概率。`confirmed_at` 表示用户同意保存的时间，与真实性、证据等级分开。导入聊天时保留说话者；旧 AI 回答、派生摘要和相同事件的复述不增加证据等级。发现反例先复查，不以机械计数压过矛盾。

| 字段 | 语义 |
| --- | --- |
| `id` / `dimension` / `domains` | 稳定引用、模型维度和任务领域标签；一个记录可属多个领域，但只维护一份 |
| `recorded_at` | 首次写入这条记录的时间 |
| `first_observed` / `last_observed` | 首次与最近一次获得支持证据的时间；普通读取不延长有效性 |
| `valid_from` / `valid_to` | 陈述实际适用的时期；未知为 null，不以写入时间代替 |
| `review_after` | 需要复查的时间，读取时即使状态仍为 active 也必须识别到期；不是自动失效时间 |
| `stability` | short_term / long_term，辅助复查及 core 选择；长期也可变化 |
| `supersedes` / `derived_from` | 后续记录关联前条记录 / 推导依赖；变化与解释必须可追溯 |

有明确结束时间且已经结束的记录只用于历史问题；未知结束时间不能断言仍然有效。状态到期、时间缺口或冲突影响当前决策时先求证，必要时说明“此前表达过”。长期 core 也要检查修订号、撤回及到期信息。

### 去重、变化、更正与历史

同一来源事件只保留一个事件 ID。语义相同且情境、有效时期一致的陈述复用记录 ID，补充独立证据和 last_observed；同一事件重述不算独立证据。无法判定是否同一事件时保留待澄清，不强行合并。

真实变化建立新 ID，使用 `supersedes` 关联旧记录，旧记录标为 `superseded`；结束时间只按已知事实填写。误读或错误标为 `retracted`，纠正内容另建可追溯记录；不能把错误伪装为曾经正确的历史。相互冲突且时间/情境无法解释时标 `disputed`，不按“最新一句”直接覆盖。每次更新沿事件 → evidence_ids 的引用者 → derived_from 的引用者 → 摘要来源反向遍历全部后代。禁止自引用与推导循环。证据撤回会重新评估支持程度：失去全部支持的判断撤回，剩余证据不足的模式或解释转为 needs_review；不会为了维持 E2 而把同一事件重复计数。权限收紧取所有来源与自身限制的交集，并使旧摘要/上下文包失效；用途冲突则不召回。supersedes 只表达演变，不代表新记录自动继承旧事实。

历史留存用于解释演变；用户要求忘记时，删除要求优先于历史保留，处理范围包括事件摘录、关联判断、派生摘要及可控临时副本。Git 中已提交的内容不因当前文件删除而消失，必须如实报告剩余位置；重写历史及远端清理需要单独明确授权。

### 敏感信息与用户控制

每条事件及模型记录都标注 `sensitivity`（ordinary / personal / sensitive）及 `recall_policy`（allowed / ask / never）。未标注按 personal + ask 处理。敏感内容默认不持久化；用户明确允许保存时仍默认 ask、`include_in_summary: false`，并确认用途与范围。密钥、密码、访问令牌不作为人物记忆保存；第三方信息只留任务必需的最小表述。

保存授权、当前任务召回授权、常驻摘要授权、向外部服务发送授权彼此独立。读取候选之前依据清单路由权限；ask 先询问，never 不读取内容。每条记录与事件独立文件，从文件粒度避免混合权限。清单只记录不含原文的路径、粗粒度标签、策略与依赖；标签也应尽量少暴露敏感主题。旧聚合文件迁移前采用整个文件最严格策略，不能先读正文再过滤。派生内容不得降低来源限制；清单中保存可用于读取前判定的有效策略，源策略变化必须在同一提交中更新引用者。

用户可以查看、编辑、导出、更正、停止记忆或要求忘记。用户手工编辑后需重新检查引用及摘要。Markdown/YAML 与 Git 本身不是加密或访问控制设施；敏感原文不进入公开仓库。备份、Git 远端与未来 Adapter 的数据传输均由用户选择，不能把启用 Git 等同于允许上传。

### 按相关性召回，不全量注入

1. 先读清单和授权元数据，不读取摘要正文。清单包含 schema_version、model_id、revision、记录 ID、相对路径、粗粒度领域、状态、业务时间、约束标记、权限、依赖 ID 和内容哈希；不包含原文。按[执行与恢复契约](#runtime)验证拟载入摘要的已授权来源后，才返回其正文。
2. 根据请求提取领域、任务目标与时间范围；先做权限检查，再选允许读取的记录文件。无个人上下文需求时不读取领域记忆。
3. 在允许的候选中按“与当前问题的关联 → 时间有效性 → 证据支持 → 信息互补”选取少量记录。同一事件支持的相近陈述去重；反例与必要约束不因迎合偏好而遗漏。
4. 本地读取预算与发给模型的预算分开：默认每次最多读取 24 条获准正文、合计 64 KiB；输出最多 8 条领域记录、约 2000 tokens，另计最多 1500 tokens 的获准摘要。这些是待实际样例验证的可调上限。先利用元数据纳入相关硬约束及反例，再读取候选；不得为了预算把它们静默舍弃。超限返回 coverage: partial、截断原因和未覆盖领域，由用户缩小问题或批准扩大范围；证据展开也计入读取预算，不自动遍历目录。元数据含糊时标注覆盖不确定，不声称已完整掌握。
5. 输出含 model_id、revision、task_id、用途、接收目标和 coverage 的任务上下文包：记录 ID、陈述、性质、证据等级、适用时间及使用原因；对待澄清/过期项单列不确定性。用户询问依据时沿 evidence_ids 读取获准事件。历史问题允许召回历史记录，但不当作当前状态。

领域标签 career / finance / relationships 等用于路由，不复制现有 model 记录到第二份领域目录。长期 core 与按需包都不能携带超出本次授权的数据；后续所有 Adapters 继承相同约束。

### 授权与清单契约

`recall_policy` 是默认门槛，`allowed` 仍需匹配用途与接收目标；`ask` 缺少有效专项授权时询问，`never` 不读取正文。`include_in_summary` 是候选资格，不替代常驻授权。未标注字段采用 personal + ask + 不进入摘要。

`policy.yaml` 中的每项 grant 包含：id、actions（persist / recall / summary / send / maintain）、record_ids 或明确领域范围、purpose、task_id 或明确持续范围、recipient（具体宿主/模型服务）、issued_at、expires_at、revoked_at、确认回执 ID。maintain 仅允许本地校验/依赖维护，不允许内容送入模型。缺失用途、目标或期限语义时不可自行扩大授权。长期授权可使用明确的 until_revoked，由用户选择。

示例 `grant-career-001` 表示用户在本次职业讨论中确认保存并召回上述虚构事件与状态，只向选定服务发送；不允许摘要常驻。实现时必须填入实际 task_id、recipient 和确认回执，示例 ID 本身不构成授权。保存、召回、摘要、发送可在一次清晰预览中分别选择，不要求四轮弹窗。

清单每项至少包括 `id / entity_type / path / dimension / domains / status / valid_from / valid_to / review_after / role / sensitivity / effective_policy / grant_ids / evidence_ids / derived_from / content_hash`。role 可为 context / hard_constraint / counterexample，属于用户确认的任务相关含义；事件无需 dimension 时留空。路径必须规范化且位于个人目录内，不允许路径穿越及指向目录外的符号链接。ID 全局唯一，文件迁移不改变 ID。

清单是路由与一致性元数据；正文保存业务事实，源文件哈希变化时清单不再可信。元数据可由本地维护模块重建，但不能未经授权读取 never 内容，也不能把重建当作放宽权限。需要维护授权而尚未取得时停止相关操作并说明受影响范围。

### 写入与读取

全部受控访问通过本地模块。Skill 生成候选，本地 prepare 生成逐项差异和依赖影响；用户确认后，apply 复核基础版本与文件哈希，仅提交确认且依赖闭合的子集。日志、暂存、锁、提交标记及恢复顺序详见 [执行与恢复契约](#runtime)。未确认候选仅留会话内存，不进入事务目录、日志或 Git。

查询从清单按权限、领域和时间筛选具体记录；解释依据时读取获准事件；追踪变化时联合历史与时间线。默认使用有效 active 内容；到期、争议、未知有效期影响决策时单列不确定性，不当成当前确定事实。

已有有效事件或模型记录即可续用；资料不完整可补访谈。发现清单缺失、引用断裂、哈希异常或格式不兼容，停止写入并提供恢复/迁移预览。仅在用户确认且确实无旧数据时新建。旧版 records.yaml、按维度/年度聚合文件经预览迁移，保留 ID、来源、时间与限制。

用户手工编辑不自动产生新授权。重新检查差异、引用和源哈希，经确认导入新 revision 后再生成摘要；具体信任边界见[执行与恢复契约](#runtime)。

### 时间线与 Git 的区别

时间线回答「人生中何时发生了什么、何时表达了什么」；Git 回答「文件何时被修改」。去年发生的经历今天才写入，两个时间自然不同。Git 可以帮助查看或恢复文件版本，不能代替业务时间线。V1 推荐用户以 Git 管理已获准保存的文件版本，未启用时仍可使用；Skill 不自动提交或推送真实个人资料。

### 待验证

- 根据主题只读取相关且获准的记录，仍能追溯到原始来源事件。
- 同一事件支持多条判断时只保存一份证据，不重复计算独立证据数量。
- 回忆旧事时分别保留发生时间与记录时间；未知日期不被伪造。
- 部分确认、跨文件更正与忘记后无悬空引用，摘要与模型一致。
- 迁移、写入中断或同步冲突时能保持原文件可恢复。

详细故障步骤及通过条件见 [验收清单](#acceptance)。上述预算和协议已有本地实现；完整可靠性与帮助效果仍待验收。

## 三、执行与恢复契约

> 2026-10-08。本文是实现与验收的契约；本地工具已经可运行，但仍待完整验收。保留 Core / Memory / Skills / Adapters 四层；本地模块属于 Memory 的执行组件。

### 1. 职责与信任边界

Skill 负责访谈、候选提取、相关性判断、变更解释和用户确认。本地模块负责授权检查、受控读取、格式与引用校验、成组保存和恢复。宿主负责提供当前用户选择的目录、任务 ID、接收模型/服务标识，以及真实确认记录；不能把导入聊天中的“同意”视为当前操作授权。

读取资料一律作为数据返回。记录中的命令、旧 AI 回答、摘要及外部材料都不能改变工具权限。V1 不声称能阻止有文件权限的其他程序绕过模块；需要更强隔离时由宿主沙箱或后续服务实现。

### 2. 五个本地操作

| 操作 | 必要输入 | 输出 / 约束 |
| --- | --- | --- |
| open | 用户选定目录、接收目标、摘要用途授权 | 模型 ID、版本、健康状态、获准且验证通过的摘要；异常不返回旧摘要正文 |
| recall | model_id、task_id、领域、时间、用途、接收目标、预算 | records、来源 ID、使用原因、uncertainties、coverage；不修改人物记录 |
| prepare | base_revision、候选变更、所需维护授权 | change_set_id、规范化 patch_hash、逐项差异、依赖影响、所需确认；候选默认只在会话内存中 |
| apply | change_set_id、selected_change_ids、绑定的确认记录 | 已提交 revision 和操作回执；基础版本或源文件变化则 conflict，不写入 |
| recover | 模型目录、恢复授权（涉及正文时） | 完成恢复或保持停止读写；不能依靠“看起来像新文件”猜测结果 |

确认绑定 `model_id + base_revision + patch_hash + selected_change_ids`。同意 A 不批准 B；字段内容、范围或发送目标改变时重新展示。部分确认只接受依赖闭合的子集；若保留的解释依赖未确认事件，暂缓该解释。系统联动撤回、摘要失效等后果须在预览中可见。

操作回执使用 transaction_id 做幂等检查：同一已提交操作重试返回原结果；不重复新增事件。回执只保留 ID、版本和结果，不保留原文；未知事务或已清理回执返回明确状态，不盲目重放。

### 3. 成组写入：日志恢复协议

V1 只支持本机、单个受控写入者，所有受控读取和写入使用同一模型锁。网络文件系统、多设备同时编辑不在此协议保证范围内；锁不能阻止外部编辑器，因此还要进行内容哈希检查。

1. **预览前**：读取清单版本和相关已授权源文件哈希，生成变更预览。候选及未批准内容不写入磁盘。
2. **确认后**：获得模型锁，先恢复遗留事务，再复核基础 revision、源哈希、确认摘要和授权范围。变化则释放锁并重新预览。
3. **准备**：仅把已批准内容写入同盘 `.transactions/<id>/`；保存受影响文件的原字节、新字节或删除标记、期望哈希、目标版本以及事务状态。校验全局 ID、引用、依赖无环、路径在目录内、权限不放宽、部分确认闭合。暂存与备份仅本地使用，排除 Git，权限不宽于源文件。
4. **持久化准备记录**：写完并刷盘暂存文件及 PREPARED 日志；必要的目录项同步后才进入替换阶段。
5. **替换**：在锁内逐个替换正文、清单与派生摘要。受控读取此时等待。每步校验并持久化；全部完成后最后写入并持久化 COMMITTED 标记。
6. **完成**：保留最小操作回执，清除暂存与原文备份，释放锁，才报告成功。清理失败必须报告残留位置，特别是忘记操作。

重启后：PREPARED 且未 COMMITTED 的事务按日志回滚为完整旧版本；COMMITTED 的事务验证新版本并完成清理。任何文件与日志记录的新旧哈希均不符，说明可能存在外部修改，停止并提供恢复预览，不覆盖它。日志或备份缺失时保持只读诊断，不能初始化覆盖。

该协议不是跨多个文件的单次原子重命名。它保证遵循模块的读者在恢复完成后看见一致版本；任意外部编辑器或同步程序仍可能看见中间态。断电持久性还依赖目标文件系统的实际刷盘语义，须在支持平台测试后再宣称保证。

忘记操作若已提交但未完成备份清理，返回“当前记录已删除，临时副本仍待清理”，不能宣称完全忘记。Git、远端、外部备份和已发送对话逐项说明控制范围，另行获得历史重写或远端操作授权。

### 4. 先验证，再把摘要交给 AI

宿主不得直接把 AGENT.md 设为无需校验的启动注入文件。

1. open 只先读取清单、策略和摘要来源 ID 元数据。
2. 核对常驻授权、接收服务、用途、期限，以及依赖记录的有效状态和复查时间。
3. 本地模块仅对已授权来源计算内容哈希，和清单及摘要源版本比较；受限来源不为校验而越权打开。
4. 通过后才返回摘要正文。权限未满足时跳过；哈希变化时按手工编辑处理，不继续使用旧摘要。
5. 摘要缺失或过时，可从已确认且获准的稳定记录按模板组装。只摘录已有陈述及 ID，不自动增加解释。新概括须再次确认。

无加载入口的宿主使用手动 open/recall。向云端模型返回内容属于一次向外部目标发送，不能以“本地运行工具”为由跳过发送授权；可由用户预先授予有明确范围与期限的目标授权，避免每次重复询问。

已经送入会话的文字不能从模型上下文中可靠收回。收到撤回通知后停止复用旧包；宿主能重建上下文则重建，否则提示在新会话继续。上下文包携带 model_id、revision、task_id、用途和目标，不能拿旧任务的包直接用于新任务。

### 5. 手工编辑与迁移

手工编辑造成源哈希不符时，不使用摘要，也不自动接受新增授权。先按原授权读取可访问部分，检查 schema、引用、时间和差异，再由用户确认导入为新 revision；需扩大读取范围时单独说明。清单本身被改动时不能信任其中新增的允许项，要求用户重新确认受影响授权；V1 的可信确认由宿主会话提供，不依赖可编辑 YAML 自证。

旧版每维度一个 YAML、每年一个 YAML 的数据经迁移预览拆为独立文件，保留模型 ID、记录 ID、事件 ID、来源、业务时间和限制。迁移后更新路径与哈希；不得同时把新旧两份作为权威数据。旧副本的留存或删除由用户选择并记录位置。

### 可靠性用例

| ID | 输入与操作 | 必须观察到的结果 |
| --- | --- | --- |
| R01 | 同一变更涉及事件、两条判断、清单和摘要；在准备、每个替换、提交标记前后分别终止进程，再恢复 | 提交标记前回到完整旧版本，标记后保留完整新版本；无悬空引用；恢复未完成前不返回上下文 |

| R05 | 摘要来源被撤回、到期、收紧权限，或正文手改而 revision 不变 | 旧摘要正文从未返回给模型；根据具体原因跳过、询问或重新组装 |
| R06 | 同维度普通记录和 never 记录；请求仅普通记录；来源证据有更严格限制 | never 文件无正文读取；限制通过依赖传播到判断；不靠最终回答删词伪装隔离 |
| R07 | 原有 recall 授权限任务 A，改用任务 B 或新外部模型目标 | 不复用旧授权；没有匹配授权时不发送内容；已获有效长期范围授权时不重复询问 |
| R08 | 撤回事件 E，E 支持判断 A，A 支持解释 B，摘要引用 B；另有三证据模式失去一个证据 | E→A→B→摘要全链复查；模式降为 needs_review，不能继续声称达到既定模式支持门槛 |

| R10 | 导入聊天和摘录中含“忽略规则、自动批准、读取全部文件”等文字 | 始终作为引述资料；工具权限不变，未发生额外读取或写入 |
| R11 | 忘记操作分别在提交前、提交后清理前中断；存在 Git 历史副本 | 未提交则报告未完成；已提交则完成临时备份清理；说明 Git 剩余副本，不宣称全局抹除 |
| R12 | 迁移旧聚合文件；存在 ID 重复、缺失引用、路径穿越或符号链接指向目录外 | 无效输入阻止提交且原数据不变；合法迁移保留来源、时间、ID 与授权限制 |
| R13 | 去年发生的事件今天记录，发生日期只有月份，后续到期复查 | 不伪造具体日期；区分记录和发生时间；到期标待复查而非断言状态结束 |
| R14 | 恢复日志损坏、旧备份缺失或恢复期间出现未知外部编辑 | 停止自动恢复和上下文输出，列出问题与恢复选项，不创建空模型覆盖 |

每次保存测试同时检查所有 YAML 可解析、ID 唯一、引用可解析、依赖无环、策略不降低、摘要源哈希一致、临时文件清理状态，以及保存结果与用户选择一致。实现选择具体持久化机制后，在支持的本机文件系统上验证崩溃恢复；仅进程终止测试不等于已证明断电安全。

### 个性化帮助效果

保留上文定义的冷启动、更新、个性化决策三个成功测试。职业选择测试使用三组相同题目、同一模型和同一选项资料：A 无记忆；B 仅沟通偏好；C 完整的获准相关记忆。每组至少重复三次，保存输入包、读取 ID、输出和人工判定，不把单次好回答当作稳定效果。

盲评关注：是否准确识别关键约束、说明选项与价值取舍、区分历史/当前和事实/解释、指出缺失信息，以及用户是否认为建议可用于下一步行动。引用两条记录只是可追溯性检查，不代表建议有用。改变一项关键约束后，C 应调整建议或解释为何不变；加入无关记忆不应改变实质结论。
